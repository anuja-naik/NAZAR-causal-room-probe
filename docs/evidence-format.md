# Evidence record and verification boundary

**Status:** draft record/schema plus a reference hash-chain utility. No signed or real evidence bundle is included.

## Intended evidence contents

The supplied concept proposes a structured record containing information such as:

- room/session identifier and timestamp;
- stimulus hash and responding flow identifier;
- statistical result and second-round outcome;
- optical candidates and approximate region;
- tested coverage and gaps;
- software version, model hash (if applicable), and limited device metadata;
- previous-record hash for a chain.

The draft schema is `schemas/evidence-record.draft.schema.json`. It is a starting point for Finale integration; field semantics, canonical serialization, optionality, and retention policy still require review.

## Three different integrity claims

Do not collapse these into one “verified” badge:

1. **Hash consistency:** a SHA‑256 hash matches the bytes/record being checked.
2. **Chain integrity:** each entry links to the previous entry and the stored hashes recompute.
3. **Signature authenticity:** a signature verifies under a known public key and trust policy.

The included `tools/evidence_chain.py` supports only the second claim (using hashes for the chain). It does **not** check a digital signature, prove when or where a capture occurred, attest sensor truth, or establish legal admissibility. The proposed Android implementation may sign a final bundle with a hardware-backed keystore key; that functionality is not present here.

## Reference chain envelope

The draft envelope is conceptually:

```json
{
  "schema_version": "nazar-evidence-chain-draft-0",
  "sequence": 0,
  "previous_hash": null,
  "record": {},
  "record_hash": "sha256-of-canonical-envelope-without-record_hash"
}
```

The hash utility uses UTF‑8 JSON with sorted keys, compact separators, and non-finite numbers rejected. This convention is a pre-event draft, not a finalized cross-language signing specification. The phone and standalone verifier must implement the same byte-level rules before any cross-device evidence is represented as verifiable.

## Verification tool behavior

```bash
python -m tools.verify_chain path/to/chain.json
```

The input must be an array of envelope objects. The tool reports chain integrity only and explicitly says `Signature: NOT CHECKED`. It is intended for utility testing; no sample chain is shipped as a real NAZAR result.

## Security and evidence cautions

- A hash chain can detect edits to a supplied chain, but an attacker able to rewrite the entire chain can recompute hashes unless a trusted signature/anchor exists.
- A valid signature would show that a key signed bytes; it would not prove the sensor was accurate, the room was authorized, or the conclusion was correct.
- Store only the evidence necessary to explain the result. Avoid raw packet payloads, room video, faces, credentials, or unnecessary device identifiers.
- Evidence tiers must be generated by an auditable rule; a language model may explain a result but must not invent confidence or change a tier.
- Do not describe this prototype as court-admissible or tamper-proof.
